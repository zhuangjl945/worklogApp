# 手机端问题登记 + 页面受理 —— 实施方案

> 适用仓库：`D:\Cursors\worklog`（Spring Boot 3.5 + MyBatis + Vue 3 / Element Plus）
> 编写日期：2026-09-08

---

## 0. 结论先行

一句话方案：**新增「服务工单（ticket）」限界上下文**，手机端用**扫码免登录 H5** 提交问题（含拍照），
管理端新增**「问题受理台」**页面接收、派单、回复，并在受理时**一键转成已有的 work_record**，
让处理过程自动进入现有工作量/费用统计。

关键取舍：

| 决策点 | 结论 | 理由 |
|---|---|---|
| 手机入口形态 | **H5 网页（二维码/链接）**，不是原生 App、不是小程序 | 零安装、零审核、同仓库同部署、内网可直接用；小程序需备案域名+HTTPS+审核 |
| 报修人身份 | **免登录 + 单号/访问令牌查进度**，可选手机号（不强制短信验证码） | 报修人是随机访客，强制注册会杀死使用率 |
| 数据归属 | 工单**不并入 work_record**，而是独立 intake 表 + 受理后生成工作记录 | 工作记录是「员工自己的产出」，报修是「外部请求」，混在一张表会污染统计且权限模型冲突 |
| 提交接口鉴权 | 新增 `/api/public/**` 白名单 + **渠道(channel) 签名 + 多维限流** | 现有 `/api/**` 全部 `authenticated()`，必须显式放行，同时要防刷 |
| 图片上传 | 复用阿里云 OSS 直传，但**新增访客态 policy**（现有 `/api/oss/policy` 强制登录） | 手机拍照必须有，且不能把登录态给访客 |
| 通知 | P0 用受理台**轮询角标**（已有同类实现），P1 接企业微信/钉钉机器人 | 与现有 `transferPollTimer` 模式一致，成本最低 |
| 权限 | P0 **按科室隔离**（同科室可受理），P1 引入 `user.role` | 系统当前无角色概念（代码注释已明说），先不阻塞上线 |

### 1.2 [P0] 口令是明文存储

`SecurityConfig#passwordEncoder` 返回 `NoOpPasswordEncoder.getInstance()`，`user.password` 为明文。
公网暴露后一旦拖库即全量失陷。处置（必须一次性做完，含存量迁移）：

```java
// SecurityConfig.java：换成 BCrypt
@Bean
public PasswordEncoder passwordEncoder() {
    // DelegatingPasswordEncoder 支持 {bcrypt} 前缀，便于平滑迁移
    return PasswordEncoderFactories.createDelegatingPasswordEncoder();
}
```

存量迁移：写一次性 `CommandLineRunner`（或用 SQL 脚本 + 后台任务），
启动时把 `password NOT LIKE '{%}'` 的记录重写为 `{bcrypt}`+原值哈希，迁移完删除该 runner。
迁移期间登录用 `passwordEncoder.matches(raw, stored)` 天然兼容（BCrypt 校验失败再按明文比对一次并回写）。

### 1.3 [P0] JWT 密钥仍是默认值

`src/main/resources/application.yml`：`jwt.secret: "change-me-to-a-long-random-secret-at-least-32-bytes"`。
攻击者可自行签发任意 userId 的 token。处置：改成 `${JWT_SECRET:}` 空默认 + 启动期校验（长度 ≥ 32 且非默认值则 fail-fast）。

```java
// JwtProps.java：新增启动校验，密钥不合规直接拒绝启动
@PostConstruct
void validate() {
    if (!StringUtils.hasText(secret) || secret.length() < 32
            || secret.startsWith("change-me")) {
        throw new IllegalStateException("jwt.secret 未配置或不满足最小长度要求，拒绝启动");
    }
}
```

同时 `jwt.expire-seconds: 43200`（12 小时）偏长，建议 PC 端 8h、并给访客令牌单独更短 TTL。

### 1.4 [P0] CORS 形同虚设

`SecurityConfig` 里 `.cors(Customizer.withDefaults())` 会去找 `CorsConfigurationSource` bean，但全仓库**没有定义**（`SecurityBeansConfig` 只 `@EnableConfigurationProperties(JwtProps.class)`）。现在同源部署所以没暴露问题，一旦手机端与后端不同源（例如 H5 丢到 CDN/另一域名）就会静默失效或全量放开。处置：显式声明白名单，且**不要用 `*` + 携带凭证的组合**。

```java
// SecurityBeansConfig.java：显式 CORS 白名单，来源从配置读取
@Bean
public CorsConfigurationSource corsConfigurationSource(JwtProps props) {
    CorsConfiguration cfg = new CorsConfiguration();
    cfg.setAllowedOriginPatterns(allowedOrigins);   // 例：https://work.example.cn
    cfg.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE", "OPTIONS"));
    cfg.setAllowedHeaders(List.of("Authorization", "Content-Type", "X-Ticket-Auth"));
    cfg.setExposedHeaders(List.of("Content-Disposition"));
    cfg.setAllowCredentials(false);                 // 纯 Bearer 认证，不需要 cookie
    cfg.setMaxAge(3600L);
    UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/api/**", cfg);
    return source;
}
```

### 1.5 [P1] 公网化必须的运行参数

- `application.yml` 增加 `server.forward-headers-strategy: framework`，否则经 Nginx 后拿到的都是代理 IP，**限流会退化成全局限流**（这是本次方案的地基）。
- 若新增 multipart 上传路径，设置 `spring.servlet.multipart.max-file-size=5MB` / `max-request-size=30MB`（默认 1MB 会导致手机拍照上传 413）。
- 部署层：HTTPS + 443 only + HSTS；MySQL `127.0.0.1` 已是本机回环（注释已说明原因），安全组不要开 3306。

## 3. 状态机（写死在服务层，别散落各处）

```
                 ┌──────────── REOPEN（报修人 24h 内可退回）────────────┐
                 ▼                                                     │
[0 待受理] ──ACCEPT/ASSIGN──> [10 处理中] ──DONE──> [20 待确认] ──CONFIRM──> [30 已完成] ──> [40 已关闭]
     │                            │
     └──REJECT(信息不全/非本职责)──> [50 已退回]  <──┘
```

约束（全部在 `TicketService` 里用「带条件的 UPDATE」实现乐观并发，与
`WorkRecordTransferController#accept` 里 `updateStatus(id, ..., 0, 1, ...)` 影响行数判 0 的写法一致）：

1. 状态跃迁必须校验前态，例：`UPDATE service_ticket SET status=10 ... WHERE id=? AND status=0`，返回 0 行即抛 `BizException(40001,"工单状态已变化，请刷新后重试")`。
2. `ACCEPT` 时若 `work_record_id` 为空则**同事务内**创建 `work_record`（`source_type='TICKET'`），失败整体回滚。
3. `CLOSE`（归档）只允许 `status IN (30,50)`；`REOPEN` 只允许 `status=20` 且 `done_time` 在 24h 内。
4. 每次跃迁写一条 `service_ticket_log`，`visible_to_reporter` 控制内部备注不外泄。
5. `due_time` 在提交时按 urgency 计算（紧急 4h / 普通 24h / 一般 72h），超时只影响展示与统计，不做自动流转。

### 4.3 公开接口契约（手机端）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/public/tickets/meta?channel={code}&sign={sig}` | 返回表单配置：渠道名、问题类型 `[{id,name}]`、是否要手机/验证码、字数与图片上限 |
| POST | `/api/public/tickets/upload-policy?channel={code}&sign={sig}` | 访客态 OSS 直传签名（仅图片、≤5MB、目录锁死 `tickets/{code}/`） |
| POST | `/api/public/tickets` | 提交问题，返回 `{ticketNo, accessToken, status, dueTime}` |
| GET | `/api/public/tickets/{ticketNo}` | 查进度（请求头 `X-Ticket-Auth: {accessToken}`），返回状态、流转轨迹、员工回复 |
| POST | `/api/public/tickets/{ticketNo}/reply` | 报修人补充说明 / 补图 |
| POST | `/api/public/tickets/{ticketNo}/confirm` | 确认完成（20 → 30） |
| POST | `/api/public/tickets/{ticketNo}/reopen` | 24h 内退回（20 → 10） |
| POST | `/api/public/tickets/{ticketNo}/rate` | 评价 1~5 |
| GET | `/api/public/tickets/{ticketNo}/image?key={objectKey}` | 工单维度的图片代理（校验 accessToken 后才从 OSS 取流） |

`meta` 只回 `id + name`，**不回 templateJson、不回 deptId、不回其它科室数据**——
这是现有 `/api/work/categories/enabled` 不能直接复用（它 `currentDeptId()` 依赖登录态）的原因。

提交校验（`PublicSubmitRequest`）：

```java
public class PublicSubmitRequest {
    @NotBlank @Size(max = 64)  private String channelCode;   // 二维码里的渠道
    @NotBlank @Size(max = 128) private String sign;          // HMAC(channelCode+ts+nonce)
    @NotBlank @Size(max = 10)  private String ts;            // 秒级时间戳，±5 分钟有效
    @NotBlank @Size(max = 32)  private String nonce;         // 一次性随机串，防重放
    @NotBlank @Size(min = 4, max = 200) private String title;
    @NotBlank @Size(min = 5, max = 5000) private String content;
    @Size(max = 200) private String location;
    @Size(max = 50)  private String contactName;
    @Pattern(regexp = "^$|^1[3-9]\\d{9}$") private String contactPhone;
    private Long categoryId;                                  // 必须属于该渠道的科室
    private Integer urgency;                                  // 1|2|3，非法值按 2
    private List<String> imageKeys;                           // 只接受本渠道前缀的 key，≤9 张
    @Size(max = 0) private String website;                    // 蜜罐字段：人类看不见，机器人会填
}
```

四条硬校验，任一不过直接 `BizException`：
1. **签名**：`sign == HMAC_SHA256(secret, channelCode + "|" + ts + "|" + nonce)`，且 `ts` 在窗口内、`nonce` 未用过 → 杜绝伪造渠道与脚本刷单。
2. **图片 key 前缀**：必须 `startsWith("tickets/" + channelCode + "/")` → 杜绝把别人的 objectKey 塞进自己工单（越权读图）。
3. **categoryId 归属**：`categoryMapper.selectById(categoryId, channel.deptId)` 非空 → 杜绝跨科室注入。
4. **蜜罐 + 限流**：`website` 非空即静默丢弃（返回假单号）；限流见 §4.6。

### 4.4 访客态图片上传（必须重构，不能复制粘贴）

现状：`OssController#policy` 内部既算签名又拼 key 又校验扩展名，且第一行就 `requireLogin()`。
**做法：把策略生成/取流逻辑抽成 `oss/OssPolicyService` 与 `oss/OssObjectService`，`OssController` 与新的访客接口共用**，避免两套 OSS 代码日后不一致（`OssController` 当前已有未提交改动，重构前先与作者确认，见 §9 风险）。

访客版与原版的差异（必须显式收紧）：

```java
// PublicTicketController.java
@PostMapping("/upload-policy")
public ApiResponse<Map<String, Object>> uploadPolicy(@RequestParam String channel,
                                                     @RequestParam String sign,
                                                     @RequestParam String ts,
                                                     @RequestParam String nonce) {
    TicketChannelEntity ch = channelService.requireValid(channel, sign, ts, nonce); // 校验+启用态
    rateLimiter.checkUpload(ip(request), ch.getId());                              // 每分钟每IP 30 次
    // 目录锁死在渠道下，只允许图片，单文件 5MB，key 由服务端生成（客户端无权指定）
    return ApiResponse.ok(ossPolicyService.visitPolicy(
            "tickets/" + ch.getChannelCode() + "/",
            IMAGE_ONLY,   // jpg/jpeg/png/gif/webp + 真实 magic-sniff（复用现有 sniff 逻辑）
            5L * 1024 * 1024));
}
```

`/api/public/tickets/{no}/image` 走服务端代理（校验 `access_token_hash` → 再从 OSS 取流），
**不要**给报修人签发 OSS 直链：直链一旦外泄，凭 URL 即可长期访问，与「凭单号+令牌」的授权模型不符。

### 4.6 限流与防刷（不引 Redis / 不引新 Maven 依赖）

`TicketRateLimiter`：`ConcurrentHashMap<String, Window>`，`Window` = 环形 60 桶（每秒）+ 定时清理（`@Scheduled` 每分钟，或首次访问时惰性淘汰）。

```java
// TicketRateLimiter.java —— 三个维度，任一超限即拒绝
public void checkSubmit(String ip, Long channelId, String phone) {
    acquire("submit:ip:" + ip,            5,  10 * 60);   // 单 IP 10 分钟 5 次
    acquire("submit:ch:" + channelId,     props.channelQpm(), 60); // 渠道每分钟配额
    if (phone != null) acquire("submit:ph:" + hash(phone), 3, 60 * 60); // 单手机号 1 小时 3 次
}
```

配套：
- 渠道日配额：`SELECT COUNT(*) FROM service_ticket WHERE channel_id=? AND create_time>=CURDATE()` ≥ `daily_limit` 则拒绝（DB 兜底，重启不丢）。
- 真实 IP：优先 `X-Forwarded-For` 第 1 段（依赖 §1.5 `forward-headers-strategy`），**不可直接信任客户端伪造的头**——只信 Nginx 追加的那一层。
- 提交响应不含「是否命中蜜罐」的差异，避免给脚本反馈信号。
- 单号生成用 `uk_ticket_no` + 冲突重试 3 次，不用 `MAX(id)+1`（并发会撞）。
- 多实例部署时内存限流失效，届时把 `TicketRateLimiter` 换成 Redis 实现（接口已隔离，只改一个类）。

### 5.2 技术选型：为什么 P0 不引入 Vant

- **P0：同仓库同 SPA，新增 `/m/**` 路由，纯手写 CSS + 原生表单控件。**
  理由：`vite.config.js` / `SecurityConfig` 白名单 / `SpaFallbackController` / Nginx **一处都不用改**，
  一次 `npm run build` 一起出包，2 天内可上线试点；移动端只需要 3 个页面、组件量极小，
  引 Vant 反而多一套按需引入配置和 30KB+ 首包。
  要点：路由 `meta: { public: true }`（`router.beforeEach` 已按此跳过 token 校验）；
  页面用 `() => import(...)` 懒加载，管理端不会被拖进移动代码。
- **P1（可选）：拆独立子项目 `web/mobile/`（Vue 3 + Vant 4）**，产物输出到 `src/main/resources/static/m/`。
  触发条件：手机首包必须 < 200KB（4G/内网弱信号）、或要做 PWA 离线填报、或页面数 > 6。
  代价：多一套构建（`vite build --config mobile.config.js`）与部署路径约定。

> 一个现实约束：`main.js` 里 `import ElementPlus from 'element-plus'` 是全量注册，
> 入口 chunk 已含整个 Element Plus。手机 H5 若走方案 P0，等于让报修人下载管理端组件库。
> 内网试点可接受；公网推广就走 P1。

### 5.3 表单必须做的体验项

- `inputmode="numeric"` + `maxlength` 计数；拍照用 `<input type="file" accept="image/*" capture="environment">`。
- 上传前**本地压缩**（`canvas` 限长边 1600px、JPEG 0.8）：手机原图 5~12MB，不压必超 5MB 限制，这是移动表单最常见的失败原因。
- 提交按钮加 `disabled + 文案「提交中…」`，并对 `nonce` 一次性使用 → 防重复提交（用户双击 + 弱网重试会产生重复工单）。
- 失败重试：`title/content` 存 `sessionStorage`，弱网刷新不丢输入。
- 定位/房间号：优先从渠道配置带默认值（如「3F 机房」），减少输入。
- `index.html` 的 `viewport` 已 OK；建议补 `theme-color` 与 `apple-mobile-web-app-capable`。
- 兼容：iOS Safari `100vh` 问题用 `100dvh`；`<meta name="format-detection" content="telephone=no">` 避免地点被渲染成拨号链接。

## 7. 二维码发放流程（业务侧，容易被忽略但决定成败）

1. 管理员在「登记渠道维护」新建渠道 → 选受理科室 + 默认问题类型 + 是否需要手机号 + 日配额。
2. 系统生成 `channelCode + sign_secret`，导出二维码内容：
   `https://{host}/m/{channelCode}?ts={ts}&nonce={n}&sign={hmac}`
   - 静态张贴（墙贴/工位卡）用**长效渠道码**：`sign` 只用于抗伪造，不用于抗重放（重放由后端限流+配额兜底）。
   - 一次性链接（微信里发给某人）用 5 分钟时效签名。
3. 打印 A5 亚克力台卡：二维码 + 单号说明 + 「进度查询：{host}/m/query」。
4. 试点：先只发 1 个渠道（例如机房/三楼），跑两周再复制。渠道 `status=0` 可即时停用而不丢历史数据。

> 关键：二维码是**唯一**的鉴权载体，`sign_secret` 泄了等于任何人都能伪造渠道。
> 所以渠道接口要支持「重置密钥并使旧码失效」（P1），且 secret 永不出现在任何列表响应里。

## 10. 风险与决策点（需要你拍板）

1. **报修人是谁**——院内/司内员工（走企微免登，可实名）还是外部客户（必须匿名+防刷更严）？影响 §4.6 力度与 §5 表单字段。
2. **是否需要值班轮转**——若受理按「值班表」自动分派，需要新增 `ticket_duty` 表；当前方案是「抢单 + 手动派单」，够用且简单。
3. **OssController 正在被改动**（`git status` 显示 ` M`）——§4.4 的重构要提前和改动者对齐，否则合并冲突会落在同一批方法上。
4. **存量工作记录统计口径**——`source_type` 是新列，现有报表（`statsByCategory` 等）不受影响；但若要「工单类工作」单独统计，需在这些 SQL 里加维度，属 P5。
5. **图片存储成本**——报修场景图片量大且长期无价值。建议加 90 天后自动清理（`ContractScheduler` 已有定时任务范式，照抄一个 `TicketCleanupScheduler`）。
6. **无角色模型**——P0 阶段任何同科室登录用户都能受理/派单/看全部本科室工单。如果这不可接受，就把 P5 的 `user.role` 提到 P1（约 +1.5 人天）。

## 附录 B：P-1 实现落定（2026-09-08，提交 `26b86ba`）——与原方案的三处偏差

### B.1 二维码不再携带 HMAC 签名，改为服务端签发 form token（原 §7 作废）

原因有两个，都是实现时才暴露出来的硬伤：
1. **一次性 nonce 与一次填表的多次请求冲突**：手机端要连调 `form-token → meta → upload-policy ×N → submit`，
   若签名里的 nonce 第一次调用就被消费，后面必然全部失败。
2. **静态张贴的二维码无法承载时效签名**：`ts` 印死在台卡上，几分钟后就扫不出来；若放宽成永久有效，就等于没有时效。
   更何况 `sign_secret` 是印在公开二维码上的，本就不是秘密。

现在的机制：渠道码本身就是能力凭证（墙上的码谁扫都能报修，这是业务本意），
防滥用靠「一次性 form token + 三维限流 + 渠道当日配额 + 蜜罐」，不需要任何打印出来的秘密。
`ticket_channel` 表因此**没有 `sign_secret` 列**。

### B.2 工单状态用 Java 枚举，不建 `ticket_status` 字典表（原 §2.2 作废）

状态与允许的跃迁强绑定。若管理员能在界面上增删状态，会出现「新状态没有任何代码路径能把它关掉」的死工单。
`work_status` 那种可编辑字典适合「业务标签」，不适合「状态机」。
前端拿状态列表请调 `GET /api/tickets/statuses`。

### B.3 不改 `OssController`，另建访客态组件

你有 118 行未提交改动落在这个文件上（`ossClientEndpoint()/endpointHost()` 那一批），
重构它必然产生冲突。而且两套策略的语义本来就不同，不是重复代码：
登录用户可传 pdf/docx 到 `work-records/` 任意子目录；访客只能把图片写进**自己那个渠道**的目录、5MB、一次性 30 秒签名。
