## 三、详细漏洞清单

### 【严重 C-1】硬编码数据库凭据进入 Git 历史并推送至两个公开远端，配置文件至今仍被跟踪

- 风险等级：严重
- 文件路径：D:\Cursors\worklog\src\main\resources\application.yml
- 行号：当前文件第 12~16 行（datasource 段）；历史提交 e266b59、58fd390、3e1526d 中的同名文件
- 风险描述：历史版本的 application.yml 明文写有数据库账号口令与 JWT 签名密钥：

  ```yaml
  username: root
  password: 1234
  secret: "change-me-to-a-long-random-secret-at-least-32-bytes"
  ```

  取证命令 `git branch -r --contains e266b59` 的结果为 origin/main、origin/dev、origin/mian、origin_gitee/main、origin_gitee/dev。含明文凭据的提交已存在于两个公开远端的全部分支，仅删除当前文件不能消除这些历史记录。
  .gitignore 中虽列有 application.yml，但该文件当前仍处于被 Git 跟踪状态（.gitignore 对已跟踪文件无效），后续把真实密钥写入该文件的改动仍会被提交并推送到远端。
  仓库中的 JWT 值是占位串，`change-me-` 前缀会被 JwtProps 启动校验直接拒绝，实际泄露的凭据是开发环境数据库 root 口令 1234。若该口令在生产/测试环境复用，则等同于全库失陷。
- 危害说明：
  1. 源码外泄即数据库凭据外泄。root 账号可直接连接并导出全库，工作记录、服务工单（含报修人姓名、手机号）、供应商银行账号、合同金额一并泄露。
  2. 凭据已进入公开仓库历史，任何克隆者均可获得，这部分泄露已无法收回。
  3. 配置文件仍在版本控制之内，真实密钥后续仍可能被再次提交。
  4. 若生产 JWT 密钥与仓库值相同，攻击者可自签任意角色（含 ADMIN）令牌，直接接管系统。
- 修复方案：

  1. 立即轮换：MySQL 业务账号口令改为强随机（≥16 位），并为应用建立非 root 的最小权限业务账号（仅 SELECT/INSERT/UPDATE/DELETE，禁 DDL、禁 FILE/PROCESS/SUPER 权限）。
  2. 停止跟踪该文件并保留本地副本：

     ```bash
     git rm --cached src/main/resources/application.yml
     git commit -m "chore: 停止跟踪 application.yml，改由 application-example.yml 提供模板"
     git update-index --skip-worktree src/main/resources/application.yml
     ```

     同时向仓库提交一份不含任何真实值的 `application-example.yml` 模板，README 指向该模板。
  3. 清洗历史：用 `git filter-repo`（或 BFG Repo-Cleaner）删除历史中的明文凭据，随后对两个远端强制推送，并在 GitHub/Gitee 侧提交清除缓存请求；同时开启远端分支保护与平台 Secret Scanning 告警。
  4. 落地前用 `gitleaks` / `trufflehog` 复扫全历史，确认命中为 0。
  5. 生产环境确保 `JWT_SECRET`、`MYSQL_PROD_PASS`、OSS AK/SK 全部经环境变量注入（当前已使用 `${ENV:}` 形式，保持），并按轮换制度定期更换。
- 参考合规依据：GB/T 22239-2019 8.1.4.1 身份鉴别、8.1.4.2 访问控制、8.1.5.5 数据保密性、8.1.4.5 安全审计；OWASP Top 10 2021 A02 加密机制失效、A05 安全配置错误；OWASP ASVS v4.0.3 V2.10（服务与依赖认证秘钥保护）、V14.2（构建与部署）；《数据安全法》第二十七条。

### 【高危 H-1】合同模块数据范围校验存在 null 短路绕过，付款计划接口无归属判定

- 风险等级：高危
- 文件路径：D:\Cursors\worklog\src\main\java\com\zjl\worklog\contract\ContractController.java
- 行号：第 385~395 行（getAndCheckContract）、第 294~297 行（getPaymentPlans）、第 133~134 行（list）
- 风险描述：合同单条操作的归属判定统一走 `getAndCheckContract()`，判定式为：

  ```java
  if (cu.getDeptId() != null && entity.getDeptId() != null
          && !cu.getDeptId().equals(entity.getDeptId())) { ... 拒绝 ... }
  ```

  任一操作数为 null 即跳过校验，请求直接放行。UserController.create 允许创建 `deptId` 为空的账号，未绑定科室的登录账号因此可以走这条短路分支，访问任意科室的合同。
  同一文件第 294~297 行的 `getPaymentPlans()` 只判 `UserContext.get()==null`，没有科室判定。第 133~134 行的列表接口 `cu.getDeptId() != null ? cu.getDeptId() : deptId` 方向相反，无科室用户可用请求参数 `deptId` 指定任意科室。
  该 Controller 16 个方法级端点中 @RequireRole 命中 0 个；`complete`/`terminate`（第 207~219 行）不校验前置状态即可推进合同状态机。
  对照证据：同仓库 D:\Cursors\worklog\src\main\java\com\zjl\worklog\ticket\TicketChannelController.java 第 256~277 行 `resolveListScope/requireDept` 采用"未绑科室即抛异常"的 fail-closed 写法，与上述判定口径不一致。
- 危害说明：普通员工（含未绑科室账号）凭自增 ID 即可读取和修改任意科室的合同，续签与删除同样不受限制；涉及字段包括合同金额、供应商、银行账号、付款凭证号、合同原件 OSS 地址。付款计划接口可按 ID 批量遍历，全单位应付/应收台账对登录用户可读。配合 H-3（供应商主数据可被任意登录用户改写，含银行账户），先改供应商收款账户、再登记付款，可构成财务欺诈链。越权同时发生在水平（跨科室）与垂直（普通员工做出财务动作）方向。
- 修复方案：

  1. 把归属判定抽成唯一入口并改为 fail-closed（建议复用 DataScope）：

     ```java
     // 无科室账号一律拒绝访问科室归属数据，禁止 null 短路
     private void requireSameDept(CurrentUser cu, Long dataDeptId) {
         if (DataScope.canCrossDept(cu)) { return; }              // 仅 ADMIN 跨科室
         if (cu.getDeptId() == null || dataDeptId == null
                 || !cu.getDeptId().equals(dataDeptId)) {
             throw new BizException(40301, "无权访问该合同");       // 不区分"不存在"与"无权"
         }
     }
     ```
  2. `getPaymentPlans()` 补 `getAndCheckContract(contractId)` 调用后再返回数据。
  3. `list()` 去掉 `cu.getDeptId() != null ? ... : deptId` 的降级分支，非 ADMIN 一律强制覆盖为本人科室。
  4. 财务敏感动作（付款登记、续签、终止、删除）补 `@RequireRole`；状态流转统一走带 `fromStatus` 的 CAS 更新（参考工单侧 `updateStatusCas`）。
  5. 建立合同表 `dept_id NOT NULL` 约束，避免继续写入无科室的记录。
- 参考合规依据：GB/T 22239-2019 8.1.4.4 访问控制（应授予管理用户所需的最小权限，实现管理员权限分离）、8.1.4.4 c) 授权主体能访问敏感的客体重用信息；OWASP Top 10 2021 A01 失效的访问控制；OWASP ASVS v4.0.3 V3.2.1（对象级授权，所有 API 参数均需校验授权）、V4.1.5。

### 【高危 H-2】服务工单行级归属判定 `requireInDept` 同样 null 短路，可跨科室受理与改单

- 风险等级：高危
- 文件路径：D:\Cursors\worklog\src\main\java\com\zjl\worklog\ticket\TicketService.java
- 行号：第 674~680 行（requireInDept）；受影响入口 D:\Cursors\worklog\src\main\java\com\zjl\worklog\ticket\TicketController.java 全部单条操作接口
- 风险描述：

  ```java
  if (ticket == null || (deptId != null && !deptId.equals(ticket.getDeptId()))) {
      throw new BizException(40401, "工单不存在或无权访问");
  }
  ```

  调用方 `deptId == null` 时条件恒假，全部工单都会通过校验。同文件第 562~565 行的 `page()` 在 `deptId == null` 时直接返回空列表，两处口径相反。
- 危害说明：未绑定科室的登录账号可跨科室操作 9 个接口（查看详情、受理、派单、回复、退回、完成、归档、转工作记录、读取报修现场照片）。工单包含报修人姓名、手机号、故障描述与现场照片，属个人信息与内部环境信息；同一账号还能改写他人工单状态，影响业务数据完整性与审计可信度。
- 修复方案：将 `requireInDept` 改为 fail-closed，并让 `page()` 与单条判定共用同一入口：

  ```java
  // 无科室账号不得访问任何按科室归属的工单
  private ServiceTicketEntity requireInDept(Long deptId, Long id) {
      ServiceTicketEntity ticket = ticketMapper.selectById(id);
      boolean crossDept = DataScope.canCrossDept(UserContext.get());
      if (ticket == null) { throw new BizException(40401, "工单不存在或无权访问"); }
      if (crossDept) { return ticket; }
      if (deptId == null || !deptId.equals(ticket.getDeptId())) {
          throw new BizException(40401, "工单不存在或无权访问");
      }
      return ticket;
  }
  ```

  补充单元测试（现有 TicketGuardTest 已用反射钉住不变量，追加"deptId 为 null 必须被拒"用例）。
- 参考合规依据：GB/T 22239-2019 8.1.4.4 访问控制、8.1.5.4 数据完整性；OWASP Top 10 2021 A01；OWASP ASVS v4.0.3 V3.2.1。

### 【高危 H-3】供应商主数据 11 个接口零鉴权，普通员工可任意增删改（含银行账号、法人、信用代码）

- 风险等级：高危
- 文件路径：D:\Cursors\worklog\src\main\java\com\zjl\worklog\supplier\SupplierController.java
- 行号：全文件（11 个方法级端点，@RequireRole 命中数 0）；第 38~43 行（next-code）

### 【高危 H-4】免登录工单接口仅由 6 位数字查询码保护，且限流可通过伪造 X-Forwarded-For 绕过

- 风险等级：高危
- 文件路径：D:\Cursors\worklog\src\main\java\com\zjl\worklog\ticket\TicketQueryCode.java；D:\Cursors\worklog\src\main\java\com\zjl\worklog\ticket\TicketService.java；D:\Cursors\worklog\src\main\java\com\zjl\worklog\ticket\PublicTicketController.java；D:\Cursors\worklog\src\main\resources\application.yml；D:\Cursors\worklog\deploy\nginx-worklog.conf
- 行号：TicketQueryCode.java 第 22 行（LENGTH=6）、第 92~94 行（digest）、第 97~101 行（matches）；TicketService.java 第 387~402 行（失败锁定）、第 351 行（setSubmitIp）、第 289~299 行；PublicTicketController.java 第 123~163 行（reply/confirm/reopen/rate/image）；application.yml 第 7 行（forward-headers-strategy: framework）；nginx-worklog.conf 第 56 行（X-Forwarded-For 追加）
- 风险描述：免登录侧共 10 个接口（读 + 写，`/api/public/**`），访问凭证是「可预测单号（`ST` + 自增 ID + 100000，TicketNoGenerator.java 第 30~35 行，类注释亦说明单号可预测）+ 6 位纯数字查询码」。6 位数字只有 10^6 空间，校验用的口令摘要为无盐 SHA-256（第 92~94 行），比对用 `String.equals`，非常量时间。
  防爆破依赖"单号 5 次 / IP 30 次 / 900 秒"三级限流（TicketRateLimiter.java 第 16~24 行为纯单机内存 Map，重启清零），而限流取用的 IP 可被伪造：`forward-headers-strategy: framework` 使 Spring 的 ForwardedHeaderFilter 采信 XFF 最左值，nginx 用 `$proxy_add_x_forwarded_for`（追加而非覆盖），客户端自带的 `X-Forwarded-For: 1.2.3.4` 因此会成为 `request.getRemoteAddr()` 的返回值。每条请求换一个伪造 IP 即不受频次约束，同时污染审计字段 `submit_ip`。
  限流器自身的 `purgeIfDue()`（第 78~93 行）在全部 key 均新鲜时无法收敛，`MAX_KEYS=20000` 可被持续制造新 key 撑满，构成内存型 DoS。
- 危害说明：
  1. 绕过限流后可对已知单号在线爆破 6 位查询码（10^6 量级，无 IP 约束下按 1k QPS 约 17 分钟/单），读取他人报修内容、现场照片、报修人手机号。
  2. 查询码同时保护读和写（补充回复、确认完成、重开、评价、上传附件），猜中查询码即可改写他人工单。
  3. 提交侧限流失效后，可向全单位刷垃圾工单，挤占受理队列。
  4. `submit_ip` 可被伪造，事后追溯与等保要求的审计可信性失效。
- 修复方案：

  1. 收口信任边界：nginx 改为覆盖式写法，只采信代理链直连地址：

     ```nginx
     proxy_set_header X-Forwarded-For $remote_addr;        # 或保持追加，但后端只取最右值
     ```

     后端不要使用 `forward-headers-strategy: framework` 采信客户端可注入的头，改为自定义 `RemoteAddrResolver`，取 XFF 最右值（即最近一跳可信代理写入的值），并在配置中显式声明可信代理网段列表。
  2. 失败锁定按单号、按手机号哈希、按真实 IP 三重统计，计数落在数据库/Redis，重启不清零；对同一单号连续失败后强制延长锁定时长（指数退避）。
  3. 把查询码从 6 位数字提升为「8 位大写字母数字（去掉易混字符）」或对未绑定手机号的工单强制生成随机码并由服务端返回一次性展示；口令摘要换成带服务端盐的 bcrypt/scrypt（该表已有 bcrypt 设施可复用）。
  4. 写操作（回复、重开、确认）与读操作分级：写操作额外要求提交时留存的手机号后四位或一次性短信/表单令牌，避免"猜中码即可改单"。
  5. 限流器 key 加容量上限与 LRU 淘汰（`LinkedHashMap` accessOrder 或 Caffeine `maximumSize` + `expireAfterWrite`），并引入 `ticket.query.fail-per-ip` 的分布式实现。

### 【中危 M-2】JWT 无吊销/登出机制，账号被禁用或降级后旧令牌在有效期内仍全量可用

- 风险等级：中危
- 文件路径：D:\Cursors\worklog\src\main\java\com\zjl\worklog\security\JwtTokenService.java；D:\Cursors\worklog\src\main\resources\application.yml；D:\Cursors\worklog\src\main\java\com\zjl\worklog\auth\AuthController.java

- 风险描述：令牌是纯无状态 HS256，服务端不保存会话：没有 `jti` 黑名单，没有登出接口，也没有版本号或签发时间戳与库表比对。角色与科室在签发时固化进 claim，`JwtAuthFilter`（第 54~62 行）解析后不再回查数据库，因此管理员改角色、禁用账号、删除账号，对已签发的令牌都不生效。唯一的复查点是用户主动调用 `/me`，业务接口不经过它。

## 五、注释与实现一致性核查

静态审计中单列一类发现：注释与文档声称的控制与实际实现不一致，以及同类判定在多处口径不同。注释与文档不能作为控制已落地的证据，以下各项均需人工复核。

1. 安全声明与实现不符，是本章优先级最高的复核点。`TicketFormTokenService` 类注释宣称"短期、一次性、绑渠道绑来源 IP"，实际 IP 从未被校验（M-10）。`TicketQueryCode.matches` 注释称"定长摘要比对"，实为 `String.equals`（L-5）。`PasswordService` 第 44、88 行注释把 `{bcrypt}` 前缀写成 `{id}` 前缀，属复制粘贴遗留。
2. 同类逻辑多处并存，判定条件不一致。null 短路（ContractController 第 390 行、TicketService 第 676 行）与 fail-closed（TicketChannelController 第 256~277 行）同时存在。分页夹逼有的接口有、有的没有（M-5）。LIKE 转义只有一处做了（L-3）。同一判定在多处复制后条件不一致，说明改动没有做全局收敛，同类越权会随新增接口继续出现（见 S-1）。
3. 缺少边界判断。`plan.getStatus()`、`contract.getContractAmount()` 直接拆箱或参与运算（M-9）。`size` 只设下限（M-5）。`readAllBytes()` 不判体积（M-7）。
4. 死代码与脆弱写法。涉及 L-1（`setUserId` 死代码）、L-4（重复常量）、L-10（`replace("..","")`）、L-12（条件拼接的范围过滤）。

## 七、整体安全评估结论

1. 总体判定为不满足上线验收基线。缺陷为 1 项严重、8 项高危，按缺陷分级定义（"严重：可直接拿库、越权拖库、硬编码密钥，必须修复，否则禁止上线"）应判不予通过、阻断上线。
2. SQL 注入与命令注入未发现。15 个 MyBatis 映射文件全部使用 `#{}` 预编译占位，无 `${}` 拼接；Java 侧无注解 SQL、无动态拼 SQL、无 `Statement`、无 `Runtime.exec`/`ProcessBuilder`、无 JDK 反序列化入口。此项符合验收要求。
3. 越权是本次影响最大的一类缺陷。数据范围判定存在三套不一致口径：fail-closed 的 `DataScope`/`TicketChannelController`、null 短路的 `ContractController`/`TicketService.requireInDept`、SQL 层条件拼接。120 个方法级端点中约 108 个受登录保护，但 6 个业务 Controller（Contract、Supplier、Oss、OssSign、WorkRecord、WorkRecordTransfer）共 56 个端点上 `@RequireRole` 命中数为 0，全部授权判断只落在"是否登录"这一层。合同与供应商两条财务链路可在无鉴权的情况下被任意普通员工读改写，构成完整的供应链付款欺诈面（H-1 + H-3 + M-9）。
4. 免登录（未授权访问）的设计强度不足。手机端 10 个免登录接口的唯一凭据是"可预测单号 + 6 位数字码"，其限流的 IP 来源可被 `X-Forwarded-For` 伪造（nginx 追加式写法，配 `forward-headers-strategy: framework` 取最左值），是一条可绕过的在线爆破路径；同一凭据同时保护读与写（H-4）。
5. 密钥管理要分两段看。当前 `application.yml` 已全部改为 `${ENV:}` 注入，并有 `JwtProps` 启动期强校验，这部分符合要求；历史明文凭据则已随 Git 传播至公开远端，配置文件至今仍被跟踪，属必须修复并复测的严重项（C-1）。
6. 数据与个人信息保护。未发现明文口令落库的新增路径（bcrypt 与存量迁移已完成），日志未打印手机号、身份证、口令。传输层全程 HTTP、附件对象级越权、令牌与查询码存 localStorage 三点叠加，保密性要求不符合（H-5、H-7、M-8）。
7. 审计与可追溯性。只有 OSS 删除有 `log.info` 记录操作人。登录事件、口令重置、角色授予与回收、权限点门槛调整、系统参数修改、财务登记均无留痕，等保 8.1.4.5 安全审计条款不符合（M-3、M-4）。
8. 可用性与健壮性。分页无上限、附件全量入内存、限流器内存无上界、跨表写无事务，四项叠加的后果是任意登录用户都能以很低成本打断服务（M-5、M-6、M-7、H-4）。
9. P0（C-1 + H-1~H-8 共 9 项）须全部整改完成并通过复测（含越权用例与凭据轮换验证），之后方可提交二次验收。P1 中危 12 项在上线后 2 个星期内整改完成，或经评审书面豁免。P2 低危与建议项纳入迭代。
10. P0 内部的顺序建议为先做凭据轮换、停止跟踪配置文件、历史清洗（C-1），再做三处 fail-closed 鉴权收口（H-1/H-2/H-3），最后做传输层与限流信任边界（H-7/H-4）。凭据轮换见效最快，后两项要等运维配合窗口。
